# Gemini Web to OpenAI Bridge

Локальный мост, который отдаёт модели Gemini из подписки **Google AI Pro** через OpenAI-совместимый API на `http://127.0.0.1:8010/v1`. Работает поверх веб-сессии gemini.google.com (библиотека `gemini_webapi`).

---

## Вход в аккаунт: один раз, без F12

Мост владеет отдельным профилем Chrome и читает сессию через Chrome DevTools Protocol.

1. Запустите `login.cmd`.
2. В открывшемся окне Chrome войдите в свой аккаунт Google.
3. Всё. Скрипт дождётся входа и сообщит, что мост авторизован.

Копировать `__Secure-1PSID` / `__Secure-1PSIDTS` вручную не нужно. Дальше мост:
- проверяет куки сессии каждые 30 секунд и сохраняет их в `.env`, когда Google их обновил;
- принудительно ротирует `__Secure-1PSIDTS` каждые 10 минут, не полагаясь на статус аккаунта;
- при сбое авторизации перечитывает куки из браузера и переподключается.

Кнопка «Забрать сессию из браузера» на дашборде делает то же самое вручную (`POST /auth/refresh`).

`login.cmd` ждёт не просто ответа браузера, а полной сессии (`degraded:false`): гостевой уровень, где доступен только `gemini-flash-lite`, за успешный вход не считается.

> Профиль моста (`.chrome-profile/`) и `.env` содержат живую сессию Google и исключены из git.
> Если вход в аккаунт сброшен Google, `login.cmd` нужно запустить повторно — это единственный ручной шаг.

> **Не запускайте второй клиент Gemini с той же сессией.** Google ротирует `__Secure-1PSIDTS`, и два
> независимых клиента гасят ротацию друг друга: мост получает `UNAUTHENTICATED` при живых на вид куках.
> По этой же причине мост больше не забирает куки из браузера по таймеру — только при отсутствии
> сессии или сбое авторизации, чтобы не затирать рабочую пару значений профилем, где вход не выполнен.

## Модели

Список соответствует тому, что реально отдаёт аккаунт (`GET /health` → `active_models`). В `GET /v1/models` флаг `known:false` означает, что реестр аккаунта ещё не получен, а `available:true` ставится только модели, которая действительно есть в этом реестре.

| ID в мосте | Модель аккаунта | Thinking | Назначение |
|---|---|---|---|
| `gemini-orchestrator` | выбирается автоматически | по маршруту | модель по умолчанию |
| `gemini-carbon` | `gemini-carbon` | да | глубокие рассуждения, архитектура |
| `gemini-pro` | `gemini-pro` | да | сложные задачи |
| `gemini-4-hydrogen-high` | `gemini-4-hydrogen` | да | кодинг с рассуждениями |
| `gemini-4-hydrogen` | `gemini-4-hydrogen` | нет | быстрый агентный кодинг |
| `gemini-flash-lite` | `gemini-flash-lite` | нет | заголовки, короткие ответы |

Маршрутизация `gemini-orchestrator`:
- запросы с инструментами и ответы на результаты инструментов → Hydrogen без Thinking (не тормозить агентный цикл);
- `reasoning_effort` = `high`/`medium` или запрос на детальный план/архитектуру → Carbon с Thinking;
- генерация заголовка чата → Flash-Lite;
- остальное → Hydrogen без Thinking.

Модификатор `@think=true` / `@think=false` в имени модели перекрывает флаг Thinking.

## Контекст и вызовы инструментов

- История передаётся целиком: без окна в 14 сообщений, без обрезки выводов инструментов, без вырезания фраз из ответов ассистента.
- Проверенный потолок промпта — **700 000 символов** (замерено сквозным тестом с контрольной меткой в самом начале). При превышении отбрасываются самые старые ходы целиком, а не рвутся посередине. Порог меняется через `MAX_PROMPT_CHARS`.
- Окно в конфиге клиента выставлено в **175 000 токенов**, а не в миллион: 700 000 символов — это примерно столько. Веб-сессия не отдаёт счётчиков токенов, поэтому `usage` — оценка «символы / 4». Раньше там считались слова, что для кода занижает расход в разы, а клиент по этим числам решает, когда сжимать контекст.
- Вызовы инструментов передаются модели как JSON-описание и разбираются из блоков ```tool_call. Нативного function calling у веб-сессии Gemini нет — это ограничение протокола, а не моста.
- Результат инструмента возвращается модели ходом `Tool Result (<имя>): …`. В системной инструкции явно сказано, что инструменты исполняет клиент, а не модель: без этого модель заявляла «у меня нет доступа к файлам» и обрывала цикл.
- Агентный цикл проверен сквозным тестом: модель прочитала `calc.py`, нашла ошибку (`a - b` вместо `a + b`), перезаписала файл, перечитала его и отчиталась — 2 раунда инструментов, 33 секунды, файл на диске изменён.
- Мост не досочиняет вызовы инструментов за модель: если модель не вызвала инструмент, в ответе будет текст.
- **Починка кривого JSON.** Модель пишет вызов руками, поэтому мост чинит висячие запятые, `True/False/None`, одинарные кавычки и обрезанный хвост (в том числе ключ, у которого не пришло значение). Проверено 12 кейсами: все проходят, а `package.json` в ответе по-прежнему не становится вызовом.
- **Близкие имена.** `read-file`, `Read_File`, `read_files` сопоставляются с реально предложенным `read_file`; неизвестное имя по-прежнему отбрасывается.
- **Проверка по схеме.** Если у вызова не хватает обязательных аргументов, мост один раз просит модель исправить, а не отдаёт битый вызов клиенту. В стриме повтор делается, только пока ничего не отправлено, иначе проза пришла бы дважды.
- **Рассуждения.** `reasoning_content` идёт в стрим отдельными дельтами. В агентных ходах thinking включён (`AGENT_THINKING=1` по умолчанию). Замер на `gemini-4-hydrogen`: с thinking — 14.7 и 15.2 с, первый токен 5.3–7.1 с, 394–790 символов рассуждений; без thinking — 13.6 с и рассуждений нет. То есть видимость стоит около секунды на раунд. `AGENT_THINKING=0` отключает.
- **Carbon не для агентных ходов.** Замер: 107.5 с на один вызов инструмента против ~15 с у Hydrogen. Оркестратор берёт Carbon только при `reasoning_effort=high` или запросе на детальный план.
- Запросы выполняются параллельно, без глобальной очереди.

## Что реализовано поверх веб-протокола

Веб-сессия Gemini не принимает параметров генерации — в `gemini_webapi` нет ни одного такого поля.
Часть семантики мост поэтому реализует сам:

- **`stop`** — ответ обрезается на первой стоп-последовательности (сама она не включается), `finish_reason: stop`. В стриме придерживается хвост длиной `len(stop)-1`, чтобы последовательность, разрезанная между чанками, всё равно ловилась.
- **`max_tokens`** — бюджет вывода по оценке «символы / 4»; при достижении генерация прекращается досрочно, `finish_reason: length`. Обрезанный ответ не разбирается на вызовы инструментов: он может оборваться посередине вызова.
- **`tool_choice`** — `"none"` убирает инструменты; `"required"` и конкретная функция ограничивают список предложенных инструментов и добавляют директиву, при неподчинении делается один повтор с усиленной директивой. Если вызова всё равно нет — честная ошибка 502, а не досочиненный вызов.
- **`/v1/responses`** — настоящий Responses API: `input` строкой или элементами, `instructions`, плоская схема `tools`, `function_call` / `function_call_output`, `max_output_tokens`. В стриме отдаются события `response.created`, `response.output_text.delta`, `response.output_text.done`, `response.completed`.
- **Отмена** — обрыв соединения клиентом останавливает генерацию в Google. Замер: оборванный запрос — 1 чанк, полный — 46 чанков за 31 с.
- **Стрим в агентных ходах** — проза и обычные код-блоки идут сразу; придерживается только то, что может стать вызовом (незакрытый JSON-блок, тег `tool_call`, XML-вызов). Префикс никогда не отступает: уже отправленный текст не приходится «отзывать».

Не применяется и не эмулируется: **`temperature` и `top_p`**. У веб-интерфейса Gemini нет этих настроек, повлиять на сэмплирование нельзя.

## Устойчивость сессии

- Статус аккаунта (`GPRiHf`) регулярно отвечает `UNAUTHENTICATED` на куках, которые прекрасно генерируют. Мост считает это предупреждением, а не приговором: раньше он отказывался обслуживать живую сессию и отдавал 502. `/auth/refresh` в спорном случае делает одну пробную генерацию, но не чаще раза в 30 секунд — иначе `login.cmd` тратил бы запрос на каждый свой опрос.
- Если Google отдал неполный список моделей (бывает только `gemini-flash-lite`), мост берёт ближайшую доступную модель и пишет `[FALLBACK]`, а не падает с «Unknown model name».
- **Подмена модели всегда видна.** В ответе поле `model` — реально ответившая модель, а блок `bridge` содержит `requested_model`, `actual_model`, `fallback` и `thinking`. `GET /v1/models` отдаёт `account_models` и флаг `available` у каждой модели. Без этого запрос к Carbon молча обслуживался Flash-Lite и выглядел как успех.
- **429 от Google — главная причина «мёртвых куки».** При обращениях с прямого IP Google помечает адрес и отвечает 429 на каждую инициализацию. Снаружи это выглядит как протухшая сессия: список моделей урезается до `gemini-flash-lite`, тариф и квота пропадают, статус — `UNAUTHENTICATED`. Лечится прокси: `GEMINI_PROXY=http://127.0.0.1:10808` в `.env`. Замер: напрямую — 1 модель и `tier: None`; через прокси — все 4 модели, `tier: PRO`, 2400 кредитов. Если 429 приходит и через прокси, помечен сам выходной узел: 429 привязан к IP, а не к кукам, поэтому нужен другой узел или пауза. Мост больше не ретраит 429 сразу и не тратит на него новую авторизацию.
- **Ротация куки не зависит от статуса.** `gemini_webapi` запускает своё автообновление только при `AVAILABLE`, а статус-эндпоинт врёт — ротация не стартовала, `1PSIDTS` старел за час. Мост вызывает `rotate_1psidts` сам каждые 10 минут и сразу пишет в `.env`.
- Регистр моделей наполняется один раз при инициализации. Если он пришёл урезанным, мост каждые 5 минут переспрашивает его тем же сеансом (без нового токена) и пишет `[MODELS]`, когда список восстановился — перезапуск для этого не нужен.

## Проверено на практике

Стресс-тесты протокола — 6 из 6:

| Проверка | Результат |
|---|---|
| Два вызова в одном ходу | оба пришли, пути разные |
| Юникод, кавычки, табы, переводы строк в аргументах | содержимое совпало посимвольно |
| Вывод инструмента 109 324 символа | метки в первой и последней строке дошли |
| Ошибка инструмента (`file not found`) | модель перешла к `list` |
| Схема из 15 инструментов | выбран нужный `grep` |
| `edit` с точными строками | `oldText`/`newText` ровно как нужно |

Реальная задача: мини-проект с двумя багами, модель должна запустить тесты, найти причины, исправить через `edit` и перезапустить тесты до зелёного. Инструменты исполняются по-настоящему, `bash` ограничен запуском `python <file>.py` в песочнице.

Известный режим отказа текстового протокола: модель ставит диагноз и возвращает план вместо правки, либо не вызывает инструмент вовсе. Против этого работают напоминание в конце промпта (не в начале — у генерационной точки) и ограниченное авто-продолжение: если инструменты были предложены, а вызова нет, мост делает до двух попыток продолжить. Если модель всё равно отказывается, её исходный ответ остаётся в силе — мост ничего не досочиняет.

## Мониторинг квот

- Дашборд: `http://127.0.0.1:8010/dashboard` (и просто `/`)
- CLI: `python quota.py`
- JSON: `GET /v1/quota`
- ProviderStudio показывает живой бейдж квоты и ссылку на дашборд.

`/v1/quota` не выдумывает числа. Если Google не отдал счётчики (статус `UNAUTHENTICATED`,
сессия ещё не инициализирована, Antigravity не запущен), все значения `remaining_credits`,
`used_credits` и проценты приходят `null`, `ok:false`, а поле `reason` объясняет причину.
Раньше в этом случае подставлялось «2400 из 2400 израсходовано», и рабочая сессия выглядела
как исчерпанный тариф. Ответ кешируется на 30 секунд, чтобы дашборд и ProviderStudio не
делали по походу в Google на каждый опрос.

## Управление

| Действие | Команда |
|---|---|
| Вход в Google | `login.cmd` |
| Запуск в фоне | `start-hidden.vbs` |
| Запуск с логами | `start.cmd` |
| Остановка | `stop.cmd` |
| Автозагрузка Windows | `install-autostart.cmd` / `uninstall-autostart.cmd` |
| Открыть дашборд | `open-dashboard.cmd` |
| Статус | `status.cmd` |

`stop.cmd` завершает только процесс моста (сверяет командную строку), а не «whatever слушает порт».
Заодно он убирает зависшие `cmd.exe`-лаунчеры от прошлых запусков.

`start.cmd` больше не встаёт на `pause`: при падении он печатает код возврата и последние
25 строк `logs/bridge.log`, после чего выходит с тем же кодом. Раньше каждый неудачный старт
оставлял вечно висящий `cmd.exe`.

## Логи

`start-hidden.vbs` не оставляет консоли, поэтому всё, что мост печатает, дублируется в
`logs/bridge.log` (ротация на 2 МБ, файл `bridge.log.1`). Туда же пишет uvicorn, включая
трейсбеки. В `/health` блок `bridge` показывает время последней ротации, её ошибку,
последнюю ошибку авторизации, число активных запросов и путь к логу. `status.cmd` печатает
`/health` и последние 20 строк лога.

## Отличия от Antigravity

Мост использует веб-сессию Gemini, а не внутренний API Antigravity. Практические следствия:

- вызовы инструментов идут через текстовый протокол, а не нативный function calling;
- агентный цикл и инструменты принадлежат вашему клиенту (OpenCode), а не Antigravity;
- квота общая с подпиской Google AI Pro и считается в тех же кредитах.

Нативный путь проверен и на текущем аккаунте недоступен. Что установлено замерами:

- OAuth-токен Antigravity лежит в Credential Manager (`gemini:antigravity`) и успешно обновляется
  клиентом `1071006060591-…`; скоупы полные (`aicode`, `cloud-platform`);
- `v1internal:listExperiments` отвечает 200 — токен живой и опознаётся бэкендом;
- `v1internal:loadCodeAssist` (в том числе с `mode=FULL_ELIGIBILITY_CHECK`, через прокси и напрямую)
  отдаёт только `allowedTiers: [standard-tier]` с `userDefinedCloudaicompanionProject: true` —
  проект Code Assist аккаунту не выдан;
- `onboardUser` завершается с пустым `cloudaicompanionProject`, а `fetchAvailableModels`,
  `retrieveUserQuotaSummary` и `streamGenerateContent` отвечают 404 на любых моделях;
- локальный RPC `GetModelResponse` у language server принимает только `{prompt, model}` — без
  сообщений и инструментов, поэтому проксировать через него агентный цикл нельзя.

Вывод: без выданного проекта Code Assist нативного function calling не получить. Это ограничение
энтайтлмента аккаунта, а не моста.

### Нативный путь проверен до конца и закрыт лицензией

Продолжение проверки с реальным GCP-проектом `gemini-code-assist-514702`, созданным в консоли:

| Клиент | Проект | Результат |
|---|---|---|
| Antigravity (`1071006060591-…`) | нет | `loadCodeAssist` без проекта, генерация 404 |
| Antigravity | имя без проекта | 403 `cloudaicompanion.licenses.selfAssign denied` |
| Antigravity | существующий | `onboardUser` 403 «no valid license», генерация 404 |
| Gemini CLI (`681255809395-…`) | существующий | 403 «no valid license» на обоих хостах |

`free-tier` («Gemini Code Assist for individuals») помечен `UNSUPPORTED_CLIENT` **у обоих клиентов**:
«This client is no longer supported for Gemini Code Assist for individuals… migrate to the Antigravity
suite». Разрешён только `standard-tier`, а он требует платной лицензии.

Google закрыл Code Assist для частных пользователей: дело не в клиенте, не в проекте и не в коде.
`codeassist.py` и `codeassist_login.py` оставлены рабочими и пройдут весь путь, если лицензия появится.
